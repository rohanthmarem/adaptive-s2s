# Open duplex speech models and fine-tuning

Research date: **2026-11-14**. Prices are USD, before tax. This is a source review, not a reproduction of training or inference benchmarks. No cloud resources were purchased.

**Decision:** use the original **Kyutai Moshiko 7B** and the official `moshi-finetune` recipe for the first controlled fine-tuning experiment. Use **PersonaPlex as a prompted inference baseline**. Do not assume PersonaPlex has an official fine-tuning pipeline. For learning from scratch, investigate the newly released **caramel-1**, with a much smaller dataset/model than its published run, or Kyutai's single-GPU Pocket TTS tutorial. None of these establishes reliable empathy from the user's tone out of the box.

## Evidence labels and scope

- **Confirmed on a primary page (P):** a repository, source file, model card, paper, or provider price page was opened and supports the stated artifact, format, or number.
- **Self-reported (S):** an author/vendor's measurements or qualitative claims. A number can be present on a primary page and still be self-reported; it is not an independent reproduction.
- **Could not verify (U):** not found, inaccessible, contradictory, or not tested on the hardware in question. “Not found” describes this search, not proof of nonexistence.

“Native full duplex” below means the model updates from incoming user audio while generating its own stream. Streaming playback of a completed answer does not meet that definition. A system that runs a separate listening/state-prediction path during speech can be duplex at system level without jointly modeling both audio streams in one autoregressive state. Release dates distinguish announcements, papers, and actual artifact releases where possible. Hub repository creation dates alone do not prove public release.

## B. Fine-tuning candidates

### B1. Moshi: the most reproducible first training path

**Public trainer:** [kyutai-labs/moshi-finetune](https://github.com/kyutai-labs/moshi-finetune), Apache-2.0. It supports **LoRA and full LM fine-tuning**, not foundation-scale training of Mimi. The [training entry point](https://github.com/kyutai-labs/moshi-finetune/blob/main/train.py) freezes Mimi and computes both text and agent audio prediction losses. The [parameter-freezing code](https://github.com/kyutai-labs/moshi-finetune/blob/main/finetune/wrapped_model.py) trains parameters named `lora`; `lora.ft_embed` additionally trains embedding parameters; full mode enables all LM parameters. Thus this is not merely a text-only assistant LoRA: learned changes can affect audio generation and timing.

**Exact audio/data contract, confirmed in source:**

- **Stereo**, aligned in time: **channel 0 / left = model**, **channel 1 / right = user**. Preserve silence, gaps and overlap. Use **24,000 Hz** as the prepared training rate; the [dataset loader](https://github.com/kyutai-labs/moshi-finetune/blob/main/finetune/data/dataset.py) requests Mimi's sample rate and resamples input, so a file's original rate need not already equal 24 kHz.
- A JSONL manifest names each WAV and its duration in seconds. The [README](https://github.com/kyutai-labs/moshi-finetune) documents this layout; paths should resolve from the launch/data setup. Inspect relative paths before training.

```json
{"path":"data_stereo/a.wav","duration":24.52}
```

- Beside each WAV, same stem `.json`, containing word text and **absolute second timestamps** for the **model channel**. This is not a whole-dialogue plain transcript or a requirement for two separate speaker transcript files. [Annotation writer](https://github.com/kyutai-labs/moshi-finetune/blob/main/annotate.py), [reader/interleaver](https://github.com/kyutai-labs/moshi-finetune/blob/main/finetune/data/interleaver.py).

```json
{"alignments":[["Hello",[0.5,0.9],"SPEAKER_MAIN"],["there",[0.9,1.2],"SPEAKER_MAIN"]]}
```

**Annotation details:** `annotate.py` uses `whisper_timestamped`, default Whisper **medium**, language **en**, and `auditok` VAD for clips longer than 10 s. It reads **channel 0**, resamples that audio to **16 kHz for ASR**, emits the sidecar above, and calls CUDA directly. These are annotation settings, not the codec's training sample rate. No paid transcription API is required. The script's default execution submits SLURM jobs; the local switch matters on a rented standalone machine. [Source](https://github.com/kyutai-labs/moshi-finetune/blob/main/annotate.py).

README command, verbatim:

```bash
python annotate.py {your jsonl file}
```

Standalone command composed from the parser, **not executed here**:

```bash
python annotate.py data.jsonl --local --lang en --whisper_model medium
```

The script skips existing sidecars. Inspect word alignment quality rather than treating generated timestamps as ground truth. For training either speaker as the agent, construct another example with channels swapped and corresponding channel-0 sidecar; that is a data transformation, not a documented automatic two-sided annotation switch. [Annotation source](https://github.com/kyutai-labs/moshi-finetune/blob/main/annotate.py).

**Default recipe and hardware:** exact selected entries from [example/moshi_7B.yaml](https://github.com/kyutai-labs/moshi-finetune/blob/main/example/moshi_7B.yaml):

```yaml
full_finetuning: false
lora:
  enable: true
  rank: 128
  scaling: 2.
  ft_embed: false
duration_sec: 100
batch_size: 16
max_steps: 2000
gradient_checkpointing: true
```

The same config sets learning rate **2e-6**, weight decay **0.1**, warm-up fraction **0.05**, first-codebook loss multiplier **100**, text-padding weight **0.5**, checkpoints every **100** steps, and adapter-only saves. Full mode requires disabling LoRA and adapter-only saves. Note the current file uses `do_eval: false`; do not blindly use stale README descriptions of differently named evaluation switches. [Config](https://github.com/kyutai-labs/moshi-finetune/blob/main/example/moshi_7B.yaml).

Official launch command, verbatim:

```bash
torchrun --nproc-per-node 1 -m train example/moshi_7B.yaml
```

Fill the manifest and run directory first. The [README benchmark](https://github.com/kyutai-labs/moshi-finetune) reports **1×H100: approximately 12k tokens/s, 39.6 GB peak allocated**, and **8×H100: approximately 10.7k tokens/s, 23.7 GB peak allocated**. These are **S**, not measurements on this Mac or an L40S. The table does not clearly establish the eight-GPU throughput aggregation convention. It also does not name the single H100's PCIe/SXM variant. **Prefer one 80 GB H100 for the first run.** A 48 GB card is plausible from allocated memory but has not been verified with this exact recipe; peak allocated is not total process/device use. Full fine-tuning memory/runtime for one GPU: **not found**.

**Data examples and outcomes:** the official [DailyTalkContiguous card](https://huggingface.co/datasets/kyutai/DailyTalkContiguous) has **CC-BY-SA-4.0** data terms. I fetched its [manifest](https://huggingface.co/datasets/kyutai/DailyTalkContiguous/resolve/main/dailytalk.jsonl): **2,541 files, 78,026.3277324263 seconds = 21.67398 hours** of stereo timeline, calculated by summing `duration`. This is not a measurement of voiced hours per speaker. The trainer links this approximately **14 GB** dataset and shows a DailyTalk loss curve; it does **not** publish a controlled before/after empathy or speaking-style score. A “20 hours / couple of hours” Kyutai social announcement was found only through a mirror; the exact primary post was not verified, so it is not used as a runtime guarantee. [Trainer](https://github.com/kyutai-labs/moshi-finetune), [unverified mirrored announcement](https://ww.twstalker.com/kyutai_labs/status/1907084896515846283).

There is stronger published evidence that corpus choice changes timing: Abe et al. use a Japanese Moshi-based model pretrained on **69k h J-Chat**, then **300 h J-Chat-Clean**, **12 h CSJ**, and/or **115 h Tabidachi**. Tabidachi-only gives **NISQA 3.12**; adding CSJ gives coherence **4.50** versus **4.32** and overall **4.20** versus **3.88**. J-Chat-Clean plus Tabidachi produces **6.32 s of gaps per 20 s**, versus **4.94 s** for Tabidachi-only. This supports data-driven pace changes, not a promise that 20 h teaches empathy. [Paper, Tables 3–4](https://aclanthology.org/2026.iwsds-1.10.pdf).

**Regressions to take seriously:**

- A community user reports that fine-tuning, including DailyTalk, increases response delays; changing `pad_mul` helps timing but degrades generation quality, and initial greetings disappear. This is a **user report, not a controlled study**. [Issue #12](https://github.com/kyutai-labs/moshi-finetune/issues/12).
- The official README warns that shortening `duration_sec` can make the model go silent sooner. This limits the apparent easy fix of tiny training windows. [README](https://github.com/kyutai-labs/moshi-finetune).
- An open **Nov 6, 2026** issue identifies frame counts being passed to an interleaver expecting seconds, causing final-chunk padding to contribute text loss. The fetched source still contains the implicated call. The issue's claimed **69% padded frames** for 100 s windows on DailyTalk is **S**; I did not reproduce its training impact. Resolve/review this before spending on the default recipe. [Issue #24](https://github.com/kyutai-labs/moshi-finetune/issues/24), [source](https://github.com/kyutai-labs/moshi-finetune/blob/main/finetune/data/interleaver.py).

**Apple Silicon:** official MLX inference exists, with Q4/Q8/BF16 and documented testing on an **M3 MacBook Pro**. Commands include `python -m moshi_mlx.local -q 4` and the corresponding Q8 form. A primary M5/32 GB peak-memory and real-time benchmark was **not found**. Weight storage alone is roughly 3.5 GB for 7B at 4 bits, but that arithmetic excludes depth transformer, codec, scales, caches and runtime; it is not an RSS claim. [Official MLX guide](https://github.com/kyutai-labs/moshi/blob/main/moshi_mlx/README.md).

Official training is CUDA-specific (`.cuda()`, CUDA memory calls, NCCL/distributed support); **MPS/MLX fine-tuning is not supported by this trainer**, and a verified completed Mac training run was not found. [Training code](https://github.com/kyutai-labs/moshi-finetune/blob/main/train.py), [Mac fine-tuning question](https://github.com/kyutai-labs/moshi-finetune/issues/19). An official [conversion script](https://github.com/kyutai-labs/moshi/blob/main/scripts/import_mlx_lora.py) loads the base plus LoRA on **CPU**, fuses them, and exports MLX tensors. This is conversion, not Mac training; conversion/requantization and the resulting custom checkpoint should be tested separately.

**Offline evaluation: YES, officially on MLX.** The [official `moshi_mlx.run_inference` source](https://github.com/kyutai-labs/moshi/blob/main/moshi_mlx/moshi_mlx/run_inference.py) reads a file at 24 kHz, feeds 1,920-sample/80 ms frames from its first channel into the user stream, samples the model stream, and writes a 24 kHz output WAV. This command is composed from that parser, not quoted from a README and not run here:

```bash
python -m moshi_mlx.run_inference --hf-repo kyutai/moshiko-mlx-q4 user.wav model.wav
```

There is no `-q` flag in this offline parser: quantization is inferred from the downloaded weight filename. It processes whole 80 ms frames and does not automatically provide an unlimited post-input answer window. Add trailing silence to the stimulus so a complete answer can occur. For a fine-tune, pass converted `--moshi-weights` and the matching `--lm-config`; preserve the correct tokenizer/codec. These are source-inspected capabilities, not a verified custom-checkpoint run. [Source](https://github.com/kyutai-labs/moshi/blob/main/moshi_mlx/moshi_mlx/run_inference.py).

**Conditioning / style tags:** Moshi's “inner monologue” is its own time-aligned planned speech text, not an arbitrary external system-prompt field or hidden reasoning API. The interleaver tokenizes sidecar word strings and places their tokens on that stream. Existing-vocabulary strings such as a textual style marker can therefore be inserted technically, but **no official general-purpose style-tag schema or validated control result was found**. A new special token needs tokenizer/embedding/output compatibility and trainable weights, not just a new JSON key. Tags may be spoken or disturb alignment; zero-duration pseudo-words are dropped. `text_conditions` is read by the data code but does not magically add a conditioner to an unconditioned base model. [Interleaver](https://github.com/kyutai-labs/moshi-finetune/blob/main/finetune/data/interleaver.py), [Moshi architecture](https://github.com/kyutai-labs/moshi).

### B2. PersonaPlex: excellent baseline, incomplete public training path

**What is actually public:** NVIDIA's repo contains inference, voice prompts and an offline evaluator. No official `train.py`, LoRA/full-fine-tuning configuration, training sidecar specification, annotation pipeline, or single-GPU training memory benchmark was found in its current tree. **Moshi architectural ancestry is not evidence that `moshi-finetune` works unchanged with PersonaPlex's hybrid prompts and loss masks.** A successful integration would need to preserve those semantics. [Official repository](https://github.com/NVIDIA/personaplex), [recursive file tree](https://api.github.com/repos/NVIDIA/personaplex/git/trees/main?recursive=1).

**Published NVIDIA training, S:** paper §4 reports **1,840 h / 105,410 service dialogs** plus **410 h / 39,322 QA dialogs**; Adam/cosine schedule, depth LR **4e-6**, temporal LR **2e-6**, **24,576 steps**, batch **32**, context **2,048 frames = 163.84 s**, **6 h on 8×A100**. A100 memory capacity and peak VRAM are not stated there. Appendix A says the released checkpoint additionally uses **7,303 Fisher conversations / 1,217 h**, with changed synthetic voices/TTS. These are not a reproducible public single-GPU LoRA recipe. [Paper §4 and Appendix A](https://arxiv.org/html/2602.06053v1).

**Data format:** no exact official on-disk training manifest, transcript/word-timestamp sidecars, channel ordering convention, or annotation command was found. Input/output inference audio is **24 kHz**. Do not label Moshi's stereo JSONL/sidecar layout “PersonaPlex's official training format.” [Model card](https://huggingface.co/nvidia/personaplex-7b-v1), [repository](https://github.com/NVIDIA/personaplex).

**How prompts work:** role text is forced onto the agent text channel while agent audio is silent; a short voice example is supplied on agent audio while text is padded. User audio is replaced with a **440 Hz** tone during this prompt region, whose training loss is masked. Inference uses voice before text. The released model supports persona via text and vocal identity/style via a voice prompt. This is strong evidence for promptability, not proof of dynamic tone-sensitive empathy. [Paper §3.1](https://arxiv.org/html/2602.06053v1), [model card](https://huggingface.co/nvidia/personaplex-7b-v1). New style tags during fine-tuning remain **unverified**; a natural-language role/style instruction is the available supported interface.

**Offline evaluation: YES, official.** Exact assistant-example command from the [README](https://github.com/NVIDIA/personaplex), with authentication already configured:

```bash
python -m moshi.offline \
  --voice-prompt "NATF2.pt" \
  --input-wav "assets/test/input_assistant.wav" \
  --seed 42424242 \
  --output-wav "output.wav" \
  --output-text "output.json"
```

The script captures output for the **same duration as the input**. Supply trailing silence. It accepts `--text-prompt` for role control, `--device` (default CUDA), local weights, voice-prompt directory, and CPU offload. README also permits offline CPU execution; real-time CPU performance is not claimed. The `.pt` preset voice is an embedding prompt, not just a path to an arbitrary WAV. [Offline implementation](https://github.com/NVIDIA/personaplex/blob/main/moshi/moshi/offline.py).

**Apple inference:** NVIDIA's card targets Linux/A100/H100; no official MLX or MPS training support was found. Community [personaplex-mlx](https://github.com/mu-hashmi/personaplex-mlx) supports live local/web and `personaplex_mlx.offline` WAV-to-WAV inference, including Q4 selection. Its README provides no controlled M5 benchmark or training recipe. The author's reported approximately 10 GB offline Q4 usage was found in a forum post, not verified on this machine. [Author's post](https://www.reddit.com/r/LocalLLaMA/comments/1r7upb5/personaplex7b_on_apple_silicon_mlx/).

Community Swift port documentation estimates **~9.5 GB total Q8** and **~6.4 GB Q4**, but reports **112 ms/frame, RTF ~1.4 on M2 Max** for Q8, and worse Q4 quality. Its top-level README separately advertises **RTF ~0.94** for the demo. These are **different/inconsistent self-reports**, not a promise of real-time M5 inference. That model document also has conflicting 8-versus-16-codebook explanations; use NVIDIA's implementation as the architectural authority. [Detailed port document](https://github.com/soniqo/speech-swift/blob/main/docs/models/personaplex.md), [top-level demo claim](https://github.com/soniqo/speech-swift).

**Published persona/style result:** NVIDIA reports released-checkpoint speaker similarity **0.65**; timing results appear in C. Identity matching is not acoustic-emotion understanding. Public community emotion/empathy fine-tunes with reproducible hours/configuration/results were **not found**. Kyutai's RL derivative is a published interactivity fine-tune, covered below. [Paper Appendix A](https://arxiv.org/html/2602.06053v1).

### B3. Sophon-Realtime: public reply LoRA, different scope

This is a credible third candidate to monitor because a [public fine-tuning guide](https://github.com/adventists-ai/sophon-realtime/blob/main/finetune/README.md) now exists. **S:** it continues the bundled **rank-16, alpha-32 tag LoRA** on the **32B thinker's LLM**, keeping encoder/projector/talker/vocoder frozen; turn decisions bypass the reply LoRA. It changes wording/persona and emitted sound tags, **not learned vocal delivery or turn-taking**. Full end-to-end fine-tuning is not provided by that guide.

Its format is standard ms-swift JSONL: `messages` with system/user/assistant roles, `<audio>` placeholders and ordered `audios` paths. Preferred input **16 kHz mono**, others resampled. No stereo model-channel target or word-timestamp file is required; assistant targets are text, audio history is context only. [Guide](https://github.com/adventists-ai/sophon-realtime/blob/main/finetune/README.md), [actual examples](https://github.com/adventists-ai/sophon-realtime/blob/main/finetune/examples/data_example.jsonl).

Selected training invocation, preserving the guide's core arguments; **abbreviated, not a complete runnable recipe**:

```bash
swift sft --custom_register_path sophon_swift/swift_register.py --model Sophon-Realtime-v1 --adapters tag_swift --tuner_type lora
```

The guide specifies BF16, batch **1**, accumulation **8**, max length **4,096**, **2 epochs**, LR **5e-5**, gradient checkpointing. It reports **~65 GB peak on H100 at ≤2,048 tokens**, not at 4,096. Runtime/steps for a measured complete run and a demonstrated empathy improvement: **not found**. It recommends **20–30% replay** from **8,797 synthetic tag conversations**, plus a **150-conversation** held-out set. Dropping tags/restarting a fresh adapter can lose expressive tag use. [Guide](https://github.com/adventists-ai/sophon-realtime/blob/main/finetune/README.md).

**Offline answer:** official file-to-file *request* client exists, but it is not equivalent to timed duplex replay. From `tag/`, this parser-inspected command sends a complete file to the local server and saves its generated speech:

```bash
python client_example.py --wav user.wav --lang en --voice ryan_en --out reply.wav
```

[Client source](https://github.com/adventists-ai/sophon-realtime/blob/main/tag/client_example.py) sends a whole encoded WAV via chat completions, then collects 24 kHz output. A ready documented CLI that feeds a recorded user track in real time with timed barge-ins and saves both streams was **not found**. Do not count turn-based file inference as verification of duplex behavior.

**Apple:** official [Mac MLX guide](https://github.com/adventists-ai/sophon-realtime/blob/main/mac/README.md), added **Nov 13**, reports Flash Q4 at **~26 GB while talking**, **36 GB recommended**, 32 GB with other apps closed. **S:** M4 Max/36 GB simulated real-time input gives **0.9–1.1 s** first response after a confident turn end and **~0.15 s** interruption stop. Live microphone reports are solicited; base M5 speed is **unverified**. This is close to the entire 32 GB memory budget. No MLX/MPS training recipe found. The [Nov 13 changelog](https://github.com/adventists-ai/sophon-realtime/blob/main/CHANGELOG.md) also documents repaired repeated/skipped words on Mac; inference bugs and model capability must be separated.

## C. How well do they hear tone?

**There is evidence of useful acoustic information and some vocal responsiveness, but insufficient evidence that a first Moshi/PersonaPlex LoRA will reliably adapt wording, pace, tone and empathy to the user's delivery.** Output expressiveness, emotion classification, and choosing an appropriate empathetic response are separate tests.

|---|---|---|
| **Full-Duplex-Bench** | Bench covers pause handling, turn taking, backchannels and interruption. [NVIDIA Table 6](https://arxiv.org/html/2602.06053v1), [official benchmark](https://github.com/DanielLin94144/Full-Duplex-Bench). | Confirms published timing evaluation, **not** emotion/sarcasm recognition or empathetic prosody. **Needed evaluation for this project (recommendation, not an established model capability):** make paired user recordings with the same words and varied sadness/frustration, urgency, pace, whisper/shout and sarcasm. Include ordinary neutral dialogues so an “empathetic” fine-tune cannot win simply by slowing down or producing comforting phrases everywhere. Static WAV replay permits controlled comparisons; live/interactive trials are still necessary because a fixed recording cannot react to what the agent says.

**caramel's exact pretokenized format:** `tokens.bin` contains uint16 `[frames,16]` (speaker A codebooks 0–7, B codebooks 0–7), or `[frames,8]` monologue; `index.npy` int64 `(offset,length)` per clip; `meta.json` records width and frame count. The public [training script](https://github.com/naklecha/caramel/blob/main/train.py) supports one process as well as NCCL DDP, but selects **CUDA else CPU**; it does **not** automatically use MPS. [README](https://github.com/naklecha/caramel).

For an educational experiment, reduce caramel's configurable dimensions/layers, freeze/reuse Mimi, and start with a small aligned stereo dataset such as DailyTalkContiguous. A **10–50M** model and **1–5 h** pilot are proposed engineering choices, **not published compute/quality results**. Expect to learn reconstruction, silence, overlap and next-token loss; do not expect meaningful conversation from such a run. A verified turnkey tiny duplex **MPS training** tutorial with memory/runtime numbers was **not found**.

### 2. Recommendation

**Choose `kyutai/moshiko-pytorch-bf16` with the official Moshi trainer for the first LoRA.** Its decisive advantage is a documented path from stereo conversations and model-side word alignments to an adapter, plus official Apple inference and file replay. Start with local offline inference and a held-out evaluation set before seeking GPU approval. Compare the original base against prompted PersonaPlex; a custom model should beat a working baseline on both content and interaction.

**Strongest argument against Moshi:** its language/reasoning and adaptive-delivery quality may be too weak for the desired product, and fine-tuning can damage turn timing. Public evidence does not show that a small Moshi fine-tune reliably learns empathy from acoustic cues. The padding issue and conversion/evaluation work make even the best documented path a research project. PersonaPlex could be the better product baseline if prompting already provides sufficient persona control; Sophon is worth testing if its vendor's paralinguistic results reproduce, but neither currently gives this developer a better-established end-to-end speech fine-tuning path.

### 3. Rough compute and cost: one LoRA run and ten

**Estimate, not a measured training duration.** Use Moshi's documented default: **1 GPU × batch16 × 100 s × 2,000 steps**, rank128 LoRA. Nominal exposure is **3,200,000 audio-timeline seconds = 888.89 h**, often repeating/padding a much smaller dataset. This is not 888.89 unique hours.

The [README](https://github.com/kyutai-labs/moshi-finetune) defines processed token accounting as steps × GPUs × batch × duration × **9 × 12.5**. Applying it gives **360,000,000 target tokens**. Dividing by reported **~12,000 tokens/s** gives **30,000 s = 8.33 h**. This assumes benchmark throughput and accounting match the selected configuration; data loading, padding, checkpointing and evaluation can change wall time. It is more defensible than repeating an unverified “couple of hours” claim.
